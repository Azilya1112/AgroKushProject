# AgroKush Backend

Spring Boot REST API for equipment maintenance management — equipment, its
location, meters and their readings, spare parts, maintenance tasks and defects.
The React client lives in a separate repository (`agro-kush-frontend`) and is
built directly against these controllers.

## Stack

- Java 21 + Spring Boot 3.5.0
- Spring Data JPA + Hibernate, PostgreSQL 16 (schema generated by `ddl-auto=update`, no migration tool)
- Spring Security + JWT (jjwt 0.11.5), stateless, BCrypt password hashing
- MapStruct 1.6.3 for entity↔DTO mapping, Lombok for boilerplate
- Bean Validation (`jakarta.validation`) on request bodies
- springdoc-openapi 2.8.5 — Swagger UI at `/swagger-ui.html`, spec at `/v3/api-docs`

## Getting started

Requires JDK 21 and a PostgreSQL database named `agro_kush`.

```bash
cp .env.example .env
```

Fill in `DB_USERNAME`, `DB_PASSWORD` and `JWT_SECRET`, then:

```bash
./mvnw spring-boot:run
```

The default profile is `local` (see `application.properties`), which points at
`localhost:5432` with `postgres/postgres` and — importantly — **disables
authentication entirely** (`LocalSecurityConfig` permits every request). Run
with `dev` or `prod` to get real JWT enforcement:

```bash
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
```

The app listens on port 8080.

## Docker

```bash
docker compose up --build
```

`.env` must exist first — `DB_USERNAME`, `DB_PASSWORD` and `JWT_SECRET` are read
by compose, not baked into any image. This file defines the whole stack, so the
frontend repository must be checked out next to this one as `../agro-kush-frontend`.

Three services start:

- **db** — `postgres:16` with a `pgdata` named volume and a `pg_isready`
  healthcheck; the backend waits for it via `depends_on: condition: service_healthy`.
  Not published to the host: only the backend reaches it, at `db:5432`.
- **backend** — built from the multi-stage `Dockerfile` (Maven + JDK 21 to build,
  `eclipse-temurin:21-jre` to run), started with `SPRING_PROFILES_ACTIVE=dev`.
  Bound to `127.0.0.1:8080` for `npm run dev` and for curl; drop that `ports`
  entry in production, where nothing should reach the API directly.
- **frontend** — nginx serving the built SPA on `localhost:3000` and proxying
  `/api/*` through to `backend:8080`.

Everything the browser touches is therefore one origin, `http://localhost:3000`:
the SPA and the API share it, so there is no second certificate, no mixed
content, and no publicly reachable backend. The frontend image is built with an
empty `VITE_API_URL` and is identical in every environment — the backend's
address lives in the proxy config, not in the bundle.

`CORS_ALLOWED_ORIGINS` must still list that origin. Spring 6 treats **any**
request carrying an `Origin` header as a CORS request without checking whether
the origin is actually foreign, and browsers attach `Origin` to every non-GET
request — including same-origin ones. Leave it out and every POST/PUT/DELETE
from the app answers `403 Invalid CORS request` while GETs keep working.

## Configuration

| Variable | Used by | Default | Notes |
|---|---|---|---|
| `SPRING_PROFILES_ACTIVE` | all | `local` | `local` / `dev` / `prod`; compose sets `dev` |
| `SPRING_DATASOURCE_URL` | dev, prod | — | e.g. `jdbc:postgresql://db:5432/agro_kush` |
| `DB_USERNAME`, `DB_PASSWORD` | dev, prod | — | also consumed by the `db` service in compose |
| `JWT_SECRET` | all | a hardcoded dev key | Base64-encoded HMAC-SHA256 key |
| `JWT_EXPIRATION` | all | `36000000` | token lifetime in ms (10 hours) |
| `CORS_ALLOWED_ORIGINS` | all | `http://localhost:3000` | comma-separated `scheme://host:port`, no trailing slash; must include the origin the SPA is served from, proxy or not |

Profiles differ only in datasource, logging and security:

| Profile | Datasource | Security | Logging |
|---|---|---|---|
| `local` | hardcoded `localhost:5432`, `postgres/postgres` | **none** — `anyRequest().permitAll()`, CORS open to `*` | SQL + transactions at DEBUG |
| `dev` | from env | JWT enforced (`SecurityConfig`) | SQL + transactions at DEBUG |
| `prod` | from env | JWT enforced | root at WARN, app at INFO |

## Authentication

`POST /api/v1/register` and `POST /api/v1/authenticate` are the only public
endpoints; both return `{"token": "<jwt>"}`. Every other request needs an
`Authorization: Bearer <token>` header.

`JwtAuthenticationFilter` extracts the subject (the user's email), loads the
`User` through `CustomUserDetailsService` and populates the SecurityContext.
Sessions are stateless and CSRF is disabled. Swagger UI and `/v3/api-docs` are
excluded from the filter chain entirely, so the docs stay reachable without a
token.

Roles (`USER`, `ADMIN`) exist on the entity and are exposed as authorities, but
no endpoint is restricted by role — see "Known issues" #4.

## Project structure

```
src/main/java/com/example/agrokushproject/
├── config/          # SecurityConfig (!local) + LocalSecurityConfig (local), JwtUtils,
│                    # JwtAuthenticationFilter, CustomUserDetailsService, OpenApiConfig
├── controller/      # one @RestController per resource
├── dto/             # request/response shapes, Bean Validation annotations
├── entity/          # JPA entities + entity/enums (Role, TaskStatus, DefectStatus, EquipmentStatus)
├── exceptions/      # GlobalExceptionHandler (@RestControllerAdvice)
├── mapper/          # MapStruct interfaces (componentModel = "spring")
├── repositories/    # Spring Data JPA (JpaRepository + JpaSpecificationExecutor)
└── service/         # interfaces + service/impl implementations
src/main/resources/  # application.properties + application-{local,dev,prod}.properties
```

## API map

Everything lives under `/api/v1`. Each resource is a collection, and the five
standard operations are always spelled the same way — shown here for
`equipment`, identical for every other collection:

| Method | Path | Meaning |
|---|---|---|
| POST | `/api/v1/equipment` | create → 201 |
| GET | `/api/v1/equipment` | list, paged and filtered → 200 |
| GET | `/api/v1/equipment/{id}` | read one → 200, 404 if absent |
| PUT | `/api/v1/equipment/{id}` | replace → 200 |
| DELETE | `/api/v1/equipment/{id}` | delete → 204 |

On `PUT`, the `{id}` in the path is authoritative: the controller copies it onto
the body before the service runs, so an `id` in the payload is ignored.

| Collection | Filters on `GET` (collection) |
|---|---|
| `/api/v1/equipment` | `name`, `status` |
| `/api/v1/locations` | `name` |
| `/api/v1/materials` | `fileName` |
| `/api/v1/spare-parts` | `name` |
| `/api/v1/tasks` | `name`, `status` |
| `/api/v1/meters` | `name`, `equipmentId` |
| `/api/v1/defects` | `name`, `equipmentId`, `defectStatus` |
| `/api/v1/users` | — (no create: there is no admin-create-user endpoint) |

Everything that is not one of those five operations:

| Method | Path | Body / params | Success |
|---|---|---|---|
| POST | `/api/v1/register` | `RegisterRequest` | 200 `{token}`, 409 if the email is taken |
| POST | `/api/v1/authenticate` | `AuthenticateRequest` | 200 `{token}`, 401 on bad credentials |
| GET | `/api/v1/users/me` | — | current user from the JWT principal |
| GET | `/api/v1/equipment/{id}/meters` | — | `List<MeterDto>` |
| GET | `/api/v1/equipment/{id}/defects` | — | `List<DefectDto>` |
| PATCH | `/api/v1/defects/{id}/status` | `?status=OPEN\|IN_PROGRESS\|RESOLVED\|CLOSED` | 200 |
| POST | `/api/v1/meters/{meterId}/readings` | `MeterReadingDto` (no `meterId` needed — the path carries it) | 201; also overwrites the meter's `currentValue` |
| GET | `/api/v1/meters/{meterId}/readings` | `from`, `to` (ISO `LocalDateTime`), `page,size,sort` | `Page<MeterReadingDto>`, newest first |
| GET | `/api/v1/meters/{meterId}/readings/latest` | — | most recent reading |
| GET | `/api/v1/meters/{meterId}/readings/total` | `from`, `to` (both required) | a bare `double` — see #6 |
| DELETE | `/api/v1/meters/{meterId}/readings/{id}` | — | 204 |

Register and authenticate keep verb-shaped paths on purpose: they are actions,
not resources.

Every collection `GET` returns Spring's `Page<T>` (`content`, `totalElements`,
`totalPages`, `number`, `size`, ...) and defaults to `size=20, sort=id`.
Name-like filters are case-insensitive `LIKE %value%`, built with JPA
`Specification`s.

### Error shapes

`GlobalExceptionHandler` produces two shapes:

```jsonc
// 400 — Bean Validation failure
{ "timestamp": "...", "status": 400, "errors": { "email": "must not be blank" } }

// 401 / 404 / 409 / 500 — everything else
{ "timestamp": "...", "status": 404, "error": "Equipment not found with id 7" }
```

`DataIntegrityViolationException` becomes 409 "Record with this value already
exists", `BadCredentialsException` becomes 401 "Invalid email or password", and
anything else becomes a 500 with a generic message — the real stack trace is
logged, never returned.

## Domain model

```
Location 1─* Equipment *─* SparePart
              │  │  │
              │  │  └── 1─* Meter 1─* MeterReading
              │  └───── 1─* Defect 1─* Material   (Material.data: byte[])
              └──────── 1─1 Material  (techPassport)

User 1─* Task *─* Equipment,   Task *─1 Location
```

Enums: `Role{USER, ADMIN}`, `TaskStatus{MAJOR_REPAIRS, CURRENT_REPAIRS,
EMERGENCY_RECOVERY_REPAIRS}`, `DefectStatus{OPEN, IN_PROGRESS, RESOLVED,
CLOSED}`, `EquipmentStatus{READY_FOR_OPERATION, FUNCTIONAL, IN_MINTENANCE,
OUT_OF_SERVICE}` — note the typo in `IN_MINTENANCE`. It is persisted as a
string, so fixing the name requires a data migration.

## Known issues

Documented rather than silently patched, so API consumers know what to expect.

1. **Update endpoints replace the whole row.** Every `updateX` service maps the
   incoming DTO to a *fresh* entity, copies the id onto it and saves that, so
   any column the DTO does not carry is set to `null`. Two concrete casualties:
   `PUT /api/v1/defects/{id}` **wipes `defectStatus`** (the DTO has no such
   field), and `PUT /api/v1/materials/{id}` **wipes the file bytes and both
   parent links**. A read-modify-write on the loaded entity would fix all of
   them at once.
2. **`DefectDto` has no `defectStatus` field.** The column exists, `findAll`
   filters on it and `PATCH /defect/{id}/status` writes it — but no response
   body ever contains it, so a client can set and filter by status yet never
   display the current value.
3. **`Material` has no file transfer endpoint.** The entity stores the bytes
   (`@Lob byte[] data`), but nothing reads or writes them. `MaterialDto`'s
   `sizeBytes` and `downloadUrl` have no entity counterpart and are always
   `null`, and `MaterialMapper` maps neither `defectId` nor `equipmentId` — so
   a material response only ever contains `id`, `fileName` and `contentType`,
   and a material cannot be attached to a defect or to equipment through the
   API at all.
4. **Roles are never enforced.** `SecurityConfig` only distinguishes
   authenticated from anonymous; there is no `hasRole` anywhere. And
   `AuthenticationService.register()` hardcodes `Role.USER`, so an `ADMIN` can
   only be created by editing the database directly.
5. **`RegisterRequest.username` is required but discarded.** Validation demands
   it, `register()` never reads it, and `User` has no such column.
6. **`/readings/total` is not a total.** `sumByMeterIdAndPeriod` computes
   `MAX(value) - MIN(value)` — consumption across the period, which is the
   sensible metric for a meter, but neither the query name nor the endpoint
   name says so.
7. **`MeterDto.currentValue` is an `int` while `Meter.currentValue` is a
   `double`.** Fractional values are truncated on the way out, and
   `PUT /api/v1/meters/{id}` writes the truncated value back.
8. **An unknown URL answers 500, not 404.** `GlobalExceptionHandler` has a
   catch-all `@ExceptionHandler(Exception.class)`, and Spring's
   `NoResourceFoundException` for an unmapped path falls into it — so a typo in
   a client URL reports "An unexpected error occurred" instead of "not found".
   Fix: handle `NoResourceFoundException` (or `ErrorResponseException`)
   explicitly before the catch-all.
9. **`spring.profiles.active=local` is the shipped default**, so a plain
   `./mvnw spring-boot:run` serves the entire API unauthenticated.
10. **`jwt.secret` has a hardcoded fallback** in `application.properties`.
    Convenient locally, but it means a `prod` deployment that forgets to set
    `JWT_SECRET` starts up happily with a publicly known signing key.
11. **Schema is managed by `ddl-auto=update`.** Fine for development; it never
    drops or renames anything, so column changes silently diverge over time. A
    migration tool (Flyway or Liquibase) is the usual next step.
12. Dead code worth cleaning up: `RecordNotFoundException` is handled but never
    thrown, `SwaggerConfig.java` contains only a package declaration, and
    `spring.main.allow-circular-references=true` papers over a dependency cycle
    instead of breaking it.

## Tests

`AgroKushProjectApplicationTests` is the default generated context-load test and
the only test in the project. It boots the full context, so it needs a reachable
database — the Docker build passes `-DskipTests` for that reason.

```bash
./mvnw test
```
